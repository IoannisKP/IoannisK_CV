Agent X

Student project · Medieinstitutet Stockholm · 2026

How could contextual guidance help new players of Escape from Tarkov, a hardcore survival shooter, without flattening the difficulty its audience plays it for? I ran eight player interviews and synthesised them into two personas and a journey map, then designed four wireframe views and tested them in three think-aloud sessions.Run with teacher guidance as part of the UX programme. My first complete research cycle.

What it produced Participants found and understood the guidance without prompting.Testing also exposed language and sample limitations worth a further round.
›Read the case studyClose

The question

New players of Escape from Tarkov abandon it early. Lowering the difficulty would remove the reason the existing audience plays it. The brief was to find out whether guidance delivered inside the world of the game could carry a newcomer through, without changing what the game is.

What I did

  1. Eight text-based interviews on Discord, spanning beginners to veterans, including one player who had quit.
  2. Synthesis into two personas, the Seeker and the Returner, and an emotional journey map.
  3. Four wireframe views of a diegetic companion that activates only after repeated failure.
  4. Three think-aloud usability sessions against the wireframes.

What came back

Participants located the guidance and understood it without being pointed at it, which was the thing being tested. The wireframes did not have to explain themselves.

What I would do differently

The three testers were aged 40 to 46 and none of them had played Tarkov, so they did not match the Seeker profile the design targets. That left one screen, which works by deliberately staying silent, impossible to evaluate properly. The next round needs actual target players, and the report says so rather than burying it.

Radio

Personal project · directing an AI-assisted iOS build · 2026

I built an internet radio player for iOS in a single working day without writing the code. I set the scope, ran a build agent, then ran a separate agent to audit its output, and tested the result on a physical device.The work was specifying it, questioning it and testing it. That is product management, not engineering.

What it produced The audit caught four faults that all looked finished, and device testing caught a network failure that code review had passed.
›Read the case studyClose

The question

If an agent can write the code, what is left for the person directing it? I wanted to find out by shipping something real in a fixed window and paying attention to where my own judgement actually mattered.

How it ran

  1. Scope set first and written down, so that finished had a definition before anything was built.
  2. One agent building against that scope.
  3. A second, separate agent auditing the first one's output, on the assumption that it was wrong until shown otherwise.
  4. Testing on a physical device rather than the simulator.

What came back

The audit found four faults in work that presented as complete. Device testing then caught a network failure that had passed code review, because the simulator's network conditions are not a phone's.

What I take from it

The generation step was the cheap part. The value was in specifying the thing precisely, refusing to accept output that only looked finished, and testing in conditions that resemble use. None of that required writing code, and all of it required knowing what to distrust.
